# Commerce Agents 功能融合设计备忘

本文记录 `D:\github\commerce-agents崩了之后重新做` 中已有产品能力如何并入当前 `commerce-agents-fullstack` 的运营中枢。目标不是把旧项目页面原样搬过来，而是把功能沉到当前“聊天入口 + 业务执行视窗 + 交付资料”的交互框架里，后续分批接真实接口。

## 1. 旧项目功能盘点

### 前端能力入口

旧项目 `client/src/capabilities/*/manifest.json` 已声明以下能力：

| 能力 | 旧 route | 产品含义 | 当前融合入口 |
| --- | --- | --- | --- |
| 商品看板 | `board` | 产品经营总览与商品管理 | 左侧“商品看板”，后续接商品上下文选择 |
| 营销活动 | `campaigns` | 活动策划、进度和结果跟踪 | 左侧“营销活动”，交付产物可一键创建活动 |
| 平台连接 | `platform` | 抖音/淘宝/JD/PDD 等平台同步状态 | 左侧“数据接入”，业务执行视窗展示数据源状态 |
| 智能洞察 | `knowledge` | 知识检索、洞察分析 | 左侧“智能洞察”，业务执行视窗资料补充来源 |
| 每日简报 | `briefing` | 自动简报与重点信息 | 后续作为“交付资料”的简报类型 |
| 系统看板 | `dashboard` | 系统运行状态与指标 | 后续放到管理视图，不进入主对话首屏 |
| 对话历史 | `history` | 历史会话与复盘 | 当前历史会话已有，后续补任务 trace |
| AI 团队介绍 | `agents` | 团队岗位与能力说明 | 业务执行视窗里的处理步骤详情 |
| 预警中心 | `alerts` | 预警信息与处理 | 左侧“预警中心”，可由任务结果触发 |
| 通用化管理 | `packages` | 领域/岗位/技能/能力包启停回滚 | 左侧“能力包管理”，后续接岗位能力和协作流程配置 |

### 后端能力模块

旧项目后端已经覆盖：

- `products.py` / `product_service.py`：商品、商品知识、素材、竞品、状态流转。
- `campaigns.py` / `campaign_service.py`：营销活动 CRUD 与执行跟踪。
- `platform_connect.py` / `platform_sync_service.py` / `platform_adapters/*`：淘宝、京东、拼多多、抖音等平台连接和同步。
- `data_import.py`：模板下载、文件上传、快速录入、素材扫描导入。
- `intelligence.py` / `intelligence_service.py`：智能洞察、长时记忆、自动驾驶。
- `briefing.py` / `briefing_service.py`：每日简报生成。
- `alerts.py` 能力由 `alert_engine.py` 支撑：主动预警、处理状态。
- `packages.py` / `package_runtime.py` / `capability_catalog.py`：能力包、技能、岗位启停回滚。
- `workspaces.py` / `workspace_service.py` / `task_tracking.py`：工作区、任务、记忆、协同上下文。
- `long_tasks.py` / `orchestration.py` / `workflow_orchestration.py` / `tool_approval_service.py`：长任务、审批、编排、审计。

这些能力适合逐步接到当前 Rust + React 项目，不建议一次性迁移所有页面。

## 2. 当前产品的信息架构

当前界面保持一个主入口：`运营智能体`。

一级体验不再拆成很多独立页面，而是围绕一次经营任务展开：

1. 用户输入经营目标。
2. 系统规划协作流程。
3. 业务执行视窗展示读取目标、分配任务、补充资料、产物预览。
4. 结果沉淀到交付资料、商品、活动、预警或能力配置。

左侧导航只暴露用户会马上理解的对象：

- 智能运营
- 商品看板
- 营销活动
- 交付资料
- 执行清单
- 智能洞察
- 平台连接
- 每日简报
- 预警中心
- 通用化管理
- 系统看板
- AI 团队介绍

其中当前已经实现可交互的是智能运营、聊天历史和执行工作台；其他项先作为后续融合的产品锚点。

## 3. 交互融合原则

### 原则一：不要把旧功能做成独立工具箱

商品、活动、知识、预警、能力包都应该成为一次任务的上下文或产物落点。例如：

- 用户输入“帮我做五一咖啡转化方案”。
- Composer 可选择一个商品上下文。
- 业务执行视窗读取商品知识、平台数据和历史活动。
- 最终产物卡提供“创建营销活动”“同步到商品知识”“生成预警规则”。

### 原则二：业务执行视窗承担过程，不承担全部业务页面

业务执行视窗只展示本轮任务过程：

- 当前处理步骤
- 工具/资料调用摘要
- 协作流程
- 产物预览
- 风险和待确认项

商品详情、活动编辑、能力包配置等重型页面后续应以弹层或工作区页承载，不塞进业务执行视窗。

### 原则三：复杂功能先变成可操作产物卡

旧项目功能进入当前产品时，优先以“产物卡按钮”落地：

| 产物 | 后续动作 |
| --- | --- |
| 运营方案 | 加入交付资料、创建执行清单 |
| 预算表 | 同步预算核算、导出表格 |
| 千川计划 | 创建营销活动、绑定平台连接 |
| 商品诊断 | 同步商品知识、生成优化任务 |
| 竞品报告 | 加入智能洞察、创建预警规则 |
| 客服话术 | 同步商品知识、创建客服 SOP |
| 能力配置建议 | 打开能力包管理、生成岗位能力和协作流程调整草案 |

### 原则四：主对话只暴露四类业务闭环

当前对话流里的能力承接入口按四类组织，而不是把旧项目菜单平铺：

| 分类 | 承接能力 | 前端交互位置 |
| --- | --- | --- |
| 上下文 | 商品看板、平台连接、智能洞察 | 发送任务前选择商品/活动/平台数据；业务执行视窗展示读取状态 |
| 执行 | 营销活动、执行清单、工作区任务 | 最终产物支持创建活动、生成清单、分配任务 |
| 交付 | 交付资料、每日简报、复盘历史 | 阶段资料和最终产物卡沉淀为文档、简报、历史 trace |
| 治理 | 预警中心、能力包管理、审批回滚 | 风险项生成预警规则，能力配置建议进入治理流 |

这样后续融合旧功能时，用户在主对话里看到的是经营闭环，而不是旧项目功能清单。

## 4. 后续分批实施建议

### 第一批：前端信息架构和上下文入口

- 左侧导航完成旧项目功能锚点：运营工作台承接商品、活动、平台、洞察、简报、预警，管理与复盘承接交付、执行清单、通用化管理、系统看板和团队说明。
- Composer 增加“商品/活动/平台数据”上下文选择入口。
- 业务执行视窗在空态展示可用数据源和能力包状态。
- 交付资料区先用静态产物卡承接：方案、预算表、活动节奏表、商品优化清单。
- 右侧工作台收起后，在页面右上角保留轻量 `工作台 0/6` 恢复控件，对话流只保留当前进度说明，不再把展开按钮压到输入区附近。

### 第二批：商品与活动真实融合

- 后端提供商品列表、商品知识、活动列表查询接口。
- 用户发送任务时可带 `product_id`、`campaign_id`。
- 岗位能力和执行计划根据上下文决定是否启用商品诊断、预算评估、投放优化。
- 最终产物支持“创建营销活动”和“同步商品知识”。

### 第三批：数据接入与平台连接

- 接入平台连接状态：抖音、淘宝、京东、拼多多。
- 执行工作台展示“数据源已连接/缺少授权/需要上传数据”。
- 工具调用摘要改成业务语言：读取成交数据、读取投放数据、读取评价数据。
- 缺数据时给用户明确补数入口。

### 第四批：预警、简报、能力包治理

- 任务结果可生成预警规则。
- 每日简报汇总本周任务、活动、异常和待办。
- 通用化管理接岗位能力和执行计划配置预览，支持启停、发布、回滚。
- 执行工作台记录审批、审计、回滚状态。

## 5. Kimi 交互借鉴边界

可借鉴：

- 极简输入入口。
- 运行中双栏工作台。
- 右侧执行工作台可收起，主工作区右上角保留轻量恢复入口。
- 子 Agent 批次化、角色卡、任务清单、产物卡。
- 完成后回到普通对话，集群不是每轮都默认开启。

不可复制：

- Kimi 品牌、Logo、K2.6、Kimi Code、Kimi Claw。
- 原始案例图、角色名称、官方文案。
- 将“Agent 集群”作为唯一卖点。当前产品应强调“电商运营工作台”和“经营闭环”。

当前实现已把右侧折叠入口改为轻量 `工作台 0/6` 恢复控件，位置固定在主工作区右上角，界面文案使用自有产品的 `执行工作台`。

## 6. 右侧执行工作台当前迭代

本轮继续收敛右侧展开态，核心目标是让它更像“本轮业务工作的可视工作区”，而不是普通功能卡片集合。

### 展开态结构

右侧执行工作台现在按三段组织：

1. 左侧业务模块：展示商品看板、营销活动、平台连接、智能洞察、每日简报、预警中心等入口，表达这些能力会作为本轮任务上下文或执行承接点。
2. 中间工作预览：展示当前工作台节点、业务输入、模型通道和产物预览，让用户明确当前系统正在处理什么、会产出什么。
3. 底部角色工具条：以轻量横向 dock 展示数据诊断、预算评估、投放优化、创意产出、运营方案、交付文档等处理角色，减少大块卡片造成的拥挤。

### 收起态结构

收起后不保留右侧窄栏，也不把入口压到输入框底部，而是在主工作区右上角保留恢复控件；对话流中只保留一条轻量过程条：

- 当前进度
- 当前阶段说明
- 当前业务过程说明

这样用户可以继续专注对话；需要查看过程时点击右上角 `工作台 0/6` 恢复右侧执行工作台。

### 旧产品能力融合方式

旧项目中的商品、活动、平台、洞察、预警、简报、能力包、历史等能力不再平铺成工具菜单，而是落到四类闭环中：

| 闭环 | 当前页面表达 | 后续接入对象 |
| --- | --- | --- |
| 上下文 | 业务模块、业务输入、资料预览 | 商品看板、平台连接、智能洞察 |
| 执行 | 执行计划、角色工具条、阶段资料 | 营销活动、执行清单、工作台任务 |
| 交付 | 产物预览、阶段资料、最终方案 | 交付资料、每日简报、复盘历史 |
| 治理 | 风险/待确认/能力承接 | 预警中心、能力包管理、审批回滚 |

这为后续接 `D:\github\commerce-agents崩了之后重新做` 的真实接口留出清晰位置，同时避免把竞品页面结构和品牌功能直接复制进当前产品。

### 本轮补充

- 1280px 等桌面宽度恢复稳定双栏，主线约 500px、右侧工作台约 460px，不再用覆盖式浮层遮住聊天。
- 右侧工作台内部的多列布局后移到更宽视口，避免在 460px 面板里强行拆成两列或三列。
- 1440px 以上扩大为宽松双栏，主对话和右侧工作台都不被挤压。
- 右侧执行工作台 header 保持在工作区顶部，收起按钮不会随内容滚动丢失。
- 收起后恢复入口固定在主工作区右上角，不再沉到底部或混在输入区附近。
- 工作台高频入口固定为 6 个：商品看板、营销活动、平台连接、智能洞察、每日简报、预警中心。
- 能力包管理、对话历史、AI 团队介绍、系统看板作为治理/复盘/管理承接能力，不再挤进右侧首屏入口。
- 页面内部高度改为跟随应用壳父容器，避免浏览器缩放后出现外层滚动和内容错位。
- 底部角色工具条在中等宽度使用 3x2，宽屏再切成 6 列，避免角色文字被挤成窄条。
- 左侧导航改为旧项目真实产品模块：运营工作台放高频业务功能，管理与复盘承接交付资料、执行清单、通用化管理、系统看板和 AI 团队介绍。
- 公开官网只能看到入口页，真实运行态以本地截图资料为准；本轮只借鉴“主线 + 可收起执行工作台 + 文件/任务可见”的交互关系，不复制竞品品牌与功能命名。
