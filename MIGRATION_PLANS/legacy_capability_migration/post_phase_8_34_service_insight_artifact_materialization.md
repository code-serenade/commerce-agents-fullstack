# Post 8-34: Service Insight Artifact Materialization

## Status

Done.

## Goal

Persist successful service after-sales and customer insight outputs as real workspace artifacts.

This keeps the service migration inside the new product framework instead of creating a separate customer service analytics system.

## Backend Change

The following service skills now expose an explicit materialization-friendly output contract:

- `service_return_handler`
- `service_nps_analyzer`
- `service_sentiment_analyzer`
- `service_nps_driver_analysis`

Successful output includes:

```text
status=success
has_data=true
adapter_status=manual_input
data_readiness=...
summary=...
```

Default sample data is disclosed with:

```text
data_readiness=calculated_from_defaults
```

This prevents the frontend from presenting deterministic examples as live store metrics.

## Workspace Artifact Change

`WorkspaceApi::materialize_agent_content_artifact` now supports:

- `service_return_handler` -> `artifactType=service_return_plan`
- `service_nps_analyzer` -> `artifactType=service_nps_report`
- `service_sentiment_analyzer` -> `artifactType=service_sentiment_report`
- `service_nps_driver_analysis` -> `artifactType=service_nps_driver_report`

Artifacts are markdown, inline, generated by `agent_session`, and use:

```text
metadata.kind=agent_generated_content
metadata.contentCategory=service
```

## API / SSE Contract

No new HTTP route was added.

The existing `workspace_artifact_created` SSE event is reused. `API_DOCS/app.md` and `API_DOCS/sse.md` document the service insight artifact types and the default-data disclosure behavior for NPS and driver analysis.

## User-Visible Change

Users can ask the service worker for return handling, NPS/CSAT analysis, sentiment triage, or satisfaction driver analysis. When the backend succeeds, the output can appear in the workspace artifact list/detail/export flow.

If NPS or driver analysis uses default sample data, the output explicitly says so through `data_readiness=calculated_from_defaults`.
