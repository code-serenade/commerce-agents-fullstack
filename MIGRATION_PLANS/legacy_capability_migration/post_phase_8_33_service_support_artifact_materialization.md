# Post 8-33: Service Support Artifact Materialization

## Status

Done.

## Goal

Persist successful core service support skill outputs as real workspace artifacts.

This keeps customer service migration inside the new product framework instead of creating a separate support document system.

## Backend Change

The following service skills now expose an explicit materialization-friendly output contract:

- `service_ticket_handler`
- `service_faq_playbook`
- `service_escalation_flow`
- `service_dsr_improvement`

Successful output includes:

```text
status=success
has_data=true
adapter_status=manual_input
data_readiness=...
summary=...
```

`service_dsr_improvement` marks default sample scores with:

```text
data_readiness=calculated_from_defaults
```

This prevents the frontend from presenting default DSR examples as live store metrics.

## Workspace Artifact Change

`WorkspaceApi::materialize_agent_content_artifact` now supports:

- `service_ticket_handler` -> `artifactType=service_ticket_playbook`
- `service_faq_playbook` -> `artifactType=service_faq_playbook`
- `service_escalation_flow` -> `artifactType=service_escalation_playbook`
- `service_dsr_improvement` -> `artifactType=service_dsr_improvement_plan`

Artifacts are markdown, inline, generated by `agent_session`, and use:

```text
metadata.kind=agent_generated_content
metadata.contentCategory=service
```

## API / SSE Contract

No new HTTP route was added.

The existing `workspace_artifact_created` SSE event is reused. `API_DOCS/app.md` and `API_DOCS/sse.md` document the service support artifact types and the default-data disclosure behavior for DSR.

## User-Visible Change

Users can ask the service worker for complaint handling, FAQ playbooks, escalation flows, or DSR improvement. When the backend succeeds, the support playbook can appear in the workspace artifact list/detail/export flow.

If DSR uses default sample scores, the output explicitly says so through `data_readiness=calculated_from_defaults`.
