# Agent Team Answer Quality And Process Binding 2026-05-16

## 需求摘要

本轮继续处理截图暴露的多智能体问答问题：

- 多岗位任务中，数据诊断、服务方案等支持岗位仍可能把“缺少真实指标、需要补数、需要复核”的可执行边界说明误判为失败。
- 最终回答不像电商虚拟员工团队交付：主回答岗位不清晰、协作岗位差异不明显、岗位之间的承接关系不够像真实团队。
- 未手动选择预设商品时，不能把历史商品、测试商品或默认商品注入为本轮商品上下文；用户只说“咖啡类商品”时，只能按类目/用户文本回答。
- 前端右侧任务过程必须绑定到每条回答，打开时不能让左侧正文滚到底，也不能压缩正文布局。

## 后端设计

- 继续使用新产品 agent runtime / task graph / SSE / workspace artifact 体系。
- 不新增数据库表。
- 不新增或修改 HTTP API。
- 不在 web-server 中直接调用 LLM。
- worker 规范化以任务图 assignment 的真实岗位为准，而不是 worker 实例默认角色，确保 `data`、`service`、`engineering` 等岗位都补齐自己的 findings、recommendations、risks 和 evidence。
- task graph 最终合成时优先选择“终端主岗”作为主回答岗位，例如运营整合节点，而不是默认使用第一个完成的支持岗位。
- 最终合成扫描岗位 evidence，明确区分：
  - 有 `context.selected_summary`：用户本轮手动选择了预设商品资料。
  - 无 `context.selected_summary`：未选择预设商品，只按用户文本、会话历史和工作区上下文理解问题。
- 最终回答增加团队合成段落：每个岗位保留独立判断、交接动作和风险边界，主岗再把岗位输入收敛成优先级、执行清单和 `final_report`，避免多岗位结果退化成一段普通聊天。

## 前端对齐

- 每条 assistant 回答自己的过程卡片提供显式入口：查看这条回答的任务过程。
- 右侧过程面板只展示当前回答对应的 runtime events。
- 打开或关闭右侧过程面板时保存并恢复聊天滚动位置，避免用户查看中间某条回答时被拉到底部。
- 右侧过程面板作为覆盖式关联资料显示，不改变中间正文的宽度和位置。
- 当前流式回答结束时也执行用户侧内容清理，再更新页面和保存历史，避免旧的内部质量校验英文只在刷新后才消失。

## 验收

- 截图中的 `data role should provide at least two findings` 和 `service role output lacks service-specific content` 不应在正常可执行缺口说明中导致节点失败。
- 多岗位回答包含主岗结论、岗位分工、协同关系、执行清单和可沉淀交付物。
- 未选商品时最终回答必须明确“不注入默认预设商品资料”。
- 打开任意一条回答的任务过程，左侧正文滚动位置保持稳定。
- 后端运行 cargo fmt/check/clippy 和相关 agent 测试。
- 前端运行 `pnpm -C frontend/apps/web rules/test/lint/build`。

## 2026-05-17 补充修复

本轮用户截图继续暴露两个问题：

- 右侧过程里仍可能把未选商品/类目级问题的资料缺口显示为红色失败。
- 普通工作区摘要和会话历史不能被当成 `context.selected_summary`，否则用户没有手动勾选商品时也可能被误判为已选商品链路。

后端修正：

- `context_loaded` 事件只把 `context.selected_summary` 作为商品摘要输出；普通 `context.summary` 不再冒充已选商品摘要。
- 任务图最终合成在未选商品链路中跳过可恢复的岗位质量缺口，不把这类缺口写成“未完成或需复核”。
- `context.selected_summary` 的检测增加否定语义过滤，`未检测到 context.selected_summary` 不能被误判为“使用了手动选择商品”。

前端对齐：

- 每条回答仍以正文内过程卡片作为“本条过程”的唯一入口，右侧过程面板只是该回答的覆盖式详情。
- 右侧面板关闭按钮需要更直观，避免用户把它理解成隐藏在滚动条里的悬浮按钮。
- 边界类事件继续展示为“边界待复核”，不再显示为阻断失败。

## 2026-05-17 二次补充修复

本轮继续处理真实 Edge 冒烟中暴露的回答质量问题：

- LLM 在没有真实外部来源时，仍可能输出“高于多数直播场景平均水平”“行业 5-10% 区间”“略高”“属于中等水平”“支付环节存在一定阻力”等看似行业对标的定性结论。
- 这些结论会让用户误以为系统已经调用外部搜索或拥有行业基准数据，不符合“没有配置外部搜索时不能伪造来源”的要求。

后端修正：

- 在 task graph 最终合成的所有用户可见路径上增加统一 `visible_non_empty` 过滤层。
- 过滤无来源的行业基准、行业区间、常见水平、略高/略低、优于/低于、付款率低等比较性判断。
- 保留“需要收集行业基准”“缺乏行业基准导致无法客观判断”等风险边界和待补数据说明。
- `下一步`、角色表格、团队合成、岗位协作明细、主岗摘要等路径统一使用可见输出过滤，避免只过滤某一个段落但从其他段落泄漏。

前端/浏览器验证：

- 继续使用每条回答正文内的“查看本条回答过程”作为唯一过程入口。
- Microsoft Edge 冒烟验证通过：无控制台错误、无千乐咖啡泄漏、无内部质量错误文本、无无来源行业基准/比较结论泄漏。
- 打开右侧过程面板后正文滚动差值为 `0`，说明右侧过程不再挤压正文，也不会把用户正在看的中间回答拉到底部。
